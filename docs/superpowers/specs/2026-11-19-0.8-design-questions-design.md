# 0.8 design questions

0.8 settles everything that would break programs before 1.0. Three design
questions were open: shared mutable references, E0304, and what a group
returns. The short version: `mut` parameters that can be passed but never
kept, E0304 lifted, and groups unchanged. All three either add to the
language or relax a rule, so none of them breaks a program that builds today.

## Why

1.0 promises that code that builds on 1.0 builds on every 1.x. Each question
had an answer that would have broken programs (stored references, a new
group result type), so they had to be decided first. Answering them without
breaking anything means 1.0 does not wait on them: the work can ship in
0.8 or later.

## Goals

- Stateful code inside one task stops threading its state by hand. The
  self-hosted compiler does it 185 times in typecheck.lmn alone, in lines
  like `(cx, st, ds) = fields_and_variants(cx, st, ds, all)`.
- A struct can hold functions, so a table of handlers can be a type with
  named fields.
- The decision on groups is written down where people will read it.

## Non-goals

- Shared state between tasks. Channels, `Shared` and `Atomic` stay the only
  way, unchanged.
- References that can be stored, returned or captured.
- Changing what `group` evaluates to.

## Anti-goals

It is a failure, even if it works, if:

- a value can change while some other name for it is in scope (aliasing);
- the language needs lifetimes or a borrow checker;
- reference cycles become possible anywhere new (today only through
  `Shared` and channels, SPEC.md section 8);
- a function's effects stop being visible from its parameters and captures.

## Constraints

- Every change goes into both compilers (`src/` and `selfhost/`), both
  backends (interpreter and C), and stays at the bootstrap fixed point.
- SPEC.md, the book, ROADMAP.md and the design doc (Claude Docs project
  `UqAJ6SrQyDNhe4KjicrS5X`, node `259b3653-1283`) are updated with it.
- Structs that hold functions are refused by `json` and `derive` the same way
  other values without a printable or comparable form already are.
- No Rust-isms in names or syntax. `mut` is already a keyword.

## Approaches considered

**Mutable references.**

1. *Second-class `mut` parameters* (picked). A function can be given a
   place to change in, for the length of the call only. This is mutable
   value semantics, as in Hylo, and Swift's `inout`. No lifetimes, because
   the reference cannot escape; no aliasing, because overlapping `mut`
   arguments are refused.
2. *Stored references* (`Ref[T]`, `&mut`). More expressive, but it needs
   either lifetimes or giving up the no-aliasing reasoning that the
   no-data-race and no-cycle guarantees rest on. Rejected.
3. *Leave it.* Tuple assignment (`(x, p) = f(p)`) already made threading
   bearable. Rejected because the self-hosted compiler shows how much it
   still costs, and because it leaves `push` as the one magic method.

**E0304.**

1. *Lift it* (picked). The rule is inconsistent: `List[fn]` and
   `Map[Str, fn]` are allowed, so a closure can already hide in a value.
   What makes a stored closure opaque is that a function's type does not say
   what it captured, which is true wherever it is stored. The existing
   rules for functions (no `dyn`, no `==`, not a map key, "runs callbacks")
   already cover a struct that holds one.
2. *Function types that carry their authority* (`fn[Net]() -> Int`). Exact,
   but a large change to the type system for a problem the existing rules
   already handle conservatively. Rejected for now; it would be additive
   later.
3. *Keep it.* Rejected: it blocks callback tables for no protection that
   lists don't already lack.

**What a group returns.**

1. *Keep the list in start order* (picked), and document that value tasks
   are for fork-join, while long-running work uses `()` tasks, which are
   freed when they finish, and a channel.
2. *A handle per task, and the group's value is the body's value*, as Swift's
   `TaskGroup` and Trio's nurseries do. Fixes a rare case (a group that runs
   for ever with tasks that return values) by breaking every group that
   exists. Rejected.

## The design

### 1. `mut` parameters

```
fn check_decl(cx: Ctx, mut st: State, d: Decl) {
    if bad(d) { st.errors.push(error(d)) }
}

let mut st = State { errors: [] }
check_decl(cx, mut st, d)          // the caller writes `mut`

fn add(mut self: Buf, x: Int) { self.items.push(x) }
let mut buf = Buf { items: [] }
buf.add(1)                         // a receiver needs no marker, as with push
```

- **Declaring.** Any parameter can be marked `mut`, including `self`. Inside
  the function it is a `mut` variable: it can be assigned, its fields and
  elements assigned, and passed on as `mut` to another call.
- **Calling.** The argument must be written `mut place`, where `place` is
  anything an assignment can have on its left (a `mut` variable, a field, a
  list element, a map entry, a path through them), and its root must be
  `mut` (E0205 otherwise). For `mut self` the receiver is the place and no
  marker is written; it too must be a `mut` place, as for `push` today.
  Writing `mut` on an argument whose parameter is not `mut`, or leaving it
  off where it is, is an error with a fix.
- **What the caller sees.** When the call returns, the place holds what the
  callee left in its parameter. Nothing else can observe the place during
  the call: the callee has no other way to reach it, and closures and tasks
  only ever hold copies.
- **Second-class.** A `mut` parameter cannot be stored, returned, captured
  by a closure (a closure gets a copy, as it does of any variable, and
  cannot assign to it, E0205 as today), or sent on a channel. It can only be
  used in place or passed on as `mut`.
- **No overlap.** Two `mut` arguments of one call, the receiver of a
  `mut self` call included, may not overlap: `f(mut a, mut a)`,
  `f(mut a, mut a.x)` and `a.add(mut a.items)` are refused. Distinct fields
  of one root do not overlap (`f(mut a.x, mut a.y)` is fine). Two elements
  or entries of the same list or map are treated as overlapping, since the
  indexes are not known when checking (`f(mut xs[i], mut xs[j])` is
  refused; take them out and put them back). A `mut` argument and a plain
  argument may name the same thing: `f(mut xs, xs)` passes the plain one as
  a snapshot taken before the call, which is how values already behave.
- **Map entries.** `mut m[k]` follows the rules for `m[k].push(x)` and
  `m[k].field = v` today.
- **Not yet, and additive later:** `mut` parameters in interface methods
  (and so on `dyn`), in foreign functions, and in function types. A function
  with a `mut` parameter cannot be used as a value (as `push` and `remove`
  cannot today, SPEC.md section 4), so `fn(mut Int)` never needs to exist.
- **Purity.** A `mut` parameter does not by itself make a function impure:
  the change is visible at the call site, as a returned value is. The
  compiler must still never reuse or move a call with a `mut` argument
  (section 14), since it writes to the caller's place.
- **`push`** is described as a built-in `mut self` method from now on; its
  behaviour does not change.

- **Panics and cancellation** (my call). A `mut` parameter is the caller's
  place, not a copy: each change the callee makes lands there as it is made.
  If the callee panics or is cancelled halfway, the place holds what had
  been written so far, and a `defer` in the caller or the callee sees that
  (section 6: a defer sees values "at the time it runs"). This is how a
  `let mut` local already behaves when its own function panics halfway
  through a loop, so a `mut` parameter behaves like code written inline.
  `Shared.update` differs on purpose: it promises the value stays as it was,
  because other tasks share it and must never see half an update; a `mut`
  place belongs to one task.
- **Nested calls** (my call). A call's arguments may not themselves take
  `mut` of a place another argument of that call takes as `mut`:
  `f(mut a, g(mut a))` is refused. It could be ordered safely, but refusing
  it is simpler to explain and can be relaxed later.

**Implementation.** In C, the callee takes a pointer to the caller's slot.
A value only that slot holds (reference count 1) is still changed in place,
so `push` through a `mut` parameter does not copy. The interpreter must give
the same partial-change behaviour on a panic or cancellation as described
above, so it passes a reference to the place (a cell, or the variable's
own slot), not a copy written back on return.

**Proof.** The self-hosted compiler is rewritten to use `mut` parameters
for its state (`st`, `cx`, `ds` and the like), and still reaches the
bootstrap fixed point. That rewrite is the test that the feature is enough.

### 2. E0304 lifted

- Struct fields, enum payloads and the type arguments of generic structs and
  enums may hold functions, however deep.
- A type that holds a function counts as holding one for the existing rules:
  it cannot become `dyn` (E0112), be a map key (E0113) or be compared
  (E0201), and a function taking one is "pure itself, runs callbacks", as one
  taking a `List[fn]` is today. `limen caps` names the path:
  `runs callbacks (via Router.on_get)`.
- E0304 is retired, as E0301 was; its entry in the error table says so.
- E0305 (channels, `Atomic` and `Shared` in fields) stays. It is about shared
  state, not authority, and nobody has needed it lifted. A closure stored in
  a field can capture one of those, exactly as a closure in a list can
  today; the struct then runs callbacks, and the caps and purity rules
  already treat it that way.

### 3. What a group returns

No change. SPEC.md section 10 and the book's concurrency chapter say
plainly: a task that returns a value is kept until the group ends, because
its value goes in the list, so value tasks are for fork-join; a group that
runs for ever (a server, a watcher) uses `()` tasks, which are freed as soon
as they finish, and sends anything it produces on a channel.

## Order and releases

Decided: 0.8 does not wait for `mut` parameters.

In 0.8:

1. E0304 lifted: both compilers and the docs.
2. Group documentation.
3. ROADMAP.md records the three decisions, including the promise that
   Limen never gets stored references, and moves `mut` parameters to a
   release of their own after 0.8.

Their own release, after 0.8:

4. `mut` parameters: checker, both backends, both compilers, formatter,
   language server, grammars, SPEC.md, the book.
5. The self-hosted compiler rewritten to use them.

## Left to the builder

- Error codes and exact messages for the new `mut` errors, in the
  existing style (what is wrong, then what to write instead), with
  quick fixes where the fix is mechanical.
- How the interpreter implements a `mut` argument.
- How lowering and the IR represent a `mut` argument, as long as the C
  backend changes values held once in place.
- Which parts of the self-hosted compiler to convert first.
