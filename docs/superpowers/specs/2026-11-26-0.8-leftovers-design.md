# 0.8 leftovers: design

Everything left open from 0.8 and earlier, except the outside security review (moved to 0.9). Branch `fix-0.8.1`, worktree `limen-fixes`, from main at `9c57365`. Every change goes into both compilers and both backends.

## Why

CI on main has been red since 0.7.4, two language rules are unspecified or disagree between the backends, and the roadmap carries small runtime gaps and one 0.6 item (incremental checking) that were never closed. The goal is a 0.8.1 with green CI and nothing on the roadmap's 0.8-and-earlier lists still open.

## Items

### 1. `sql-wal` on Linux

macOS's SQLite keeps `-wal` and `-shm` after the last connection closes (persistent WAL); Linux's deletes them. The test pins the macOS behaviour, so it fails on Linux.

Decision (mine): make it the same everywhere by turning persistent WAL off on every connection (`SQLITE_FCNTL_PERSIST_WAL` = 0 in `ready`), so the last close checkpoints and removes both files on every platform. The test then expects `false false`. Cost if wrong: a program on macOS that relied on the files staying sees them go, which SQLite documents as the normal behaviour.

### 2. macOS CI: deep C from an `else if` chain

A 1000-link `else if` ladder emits C nested 1005 brackets deep. Apple clang 21 accepts it; the CI runner's older clang stops at 256 (`fatal error: bracket nesting level exceeded`).

Decision: emit an `else if` chain flat in C (`} else if (...) {` with each branch's statements in its own block), so the nesting stays constant however long the chain. Both `src/cgen.ml`/`src/lower.ml` and `selfhost/`. Test: the existing `chain-else-if-runs` plus a check that the emitted C's bracket depth stays under 256.

### 3. `select`: guard before channel and value

Both backends evaluate an arm's guard first, then its channel, then its value, arm by arm. SPEC.md:1058 says "in order" without saying the guard comes first.

Decision: SPEC.md says what both backends do. No code change.

### 4. Index order in a place (a real bug)

For `ys[j][{ j = 0; 0 }] = 5` with `ys = [[1,2],[3,4]]` and `j = 1`, the interpreter gives `[[5, 4], [3, 4]]` and native `[[5, 2], [3, 4]]`. The interpreter re-evaluates a place's indexes at every level of the write (side effects run more than once, and OCaml's tuple evaluation order decides the rest); native reads a variable index after a later index changed it.

Decision: SPEC.md section 5 states it fully: the right-hand side first (as today), then the place's root and its indexes and keys left to right, each evaluated exactly once, each variable read where it is written. Interpreter: evaluate the indexes once into a list of keys, then read and write through it, as the `mut` argument path (`arg_cell`) already does. Native: `lower_place` lowers each index through the same `lower_arg` rule reads use (copy a variable that a later index changes). Both compilers. Tests run in both backends: the case above (`[[1, 2], [5, 4]]`), an index with a printed side effect (printed once), map keys, and `push`/`remove` on a place. The existing E0214 refusal for an index assigning a variable another index of a `mut` place reads stays: it is still the clearer rule for `mut` arguments.

### 5. Bytes in the cross-check

Add an `xc-bytes` area to `test/crosscheck.ml`: `len`, `is_empty`, `get`, `slice`, `to_list`, `to_str`, indexing and `+`, on edge and random byte strings, with out-of-range indexes going through `catch`. Drawn last from the seed stream so the other areas' outputs stay the same.

### 6. The roadmap's smaller items

- **`Fs` methods.** Add `copy(from, to)`, `touch(path)` (set the modified time to now, create an empty file if missing), `set_executable(path, on: Bool)` and `read_link(path) -> Result[Str, IoError]`, each walked from the grant like every other `Fs` operation, `copy`, `touch` and `set_executable` refused on a read-only `Fs`, `read_link` returning the link's text without following it. End to end in both checkers, both backends, the C runtime, the interpreter's stubs, SPEC and the book's `Fs` table. The build cache (`selfhost/native.lmn`) then uses `fs.copy` and `fs.touch` instead of `cp` and `touch` through `Exec`, and the `--grant exec=cp --grant exec=touch` flags go. `compiler_id` keeps running `readlink` on `/var/db/xcode_select_link` through `Exec`, because that path is outside any `Fs` grant (my call).
- **Cancellation inside a sort and a fill loop.** Native: the merge sort checks for cancellation once per pass and every 4096 merges; the fill fast path stores in chunks of 65,536 with a check between chunks. Interpreter: the sort's comparison checks every 4096 comparisons. A cancelled sort leaves the list as it was.
- **Interpreter thread pool for blocking calls.** Replace the thread per blocking foreign call and per SQLite statement with a fixed pool (one thread per core, at least 4, growing to 64 if every thread is busy, as the native runtime's pool does), keeping the pipe that wakes the scheduler.
- **Split builds keep static what no other piece calls.** After the pieces are cut, a function whose name appears in no other piece and in no shared text (header, variables, vtables) keeps `static`, and its prototype stays in its own piece. Both `src/native.ml` and `selfhost/native.lmn`; the emitted C is checked to still build and run the same.

### 7. Review minors

- Hover on a `mut` parameter's declaration shows `mut` (`src/lsp.ml:178`).
- Grammar accept and reject samples with `mut` (a `mut` default and `mut` on a foreign parameter are rejects).
- The Bytes index panic says "for bytes of length N" (it says "list").
- `Core.rand_le` checks its bounds and raises `Invalid_argument` instead of writing past the buffer.
- The splitmix increment is defined once, in C, and read by `core.ml` through an external.
- The interpreter's `mut` path place no longer copies the outer list on every call (it writes through the cell in place when the list is held once).
- A labelled intermediate call moved by `keep_order` no longer reports twice.

### 8. Incremental checking (0.6)

Today every edit re-parses the open file and every module it uses, and checks the whole program (0.1 s to 0.3 s on the largest programs here). Diagnostics are published for the edited file only.

Decision, in two steps, the second only if the first leaves it slow:

1. **Cache what didn't change.** Parsed modules are kept between checks, keyed by path and text, so an edit re-parses one file; the standard library is parsed once per server. The check still runs over the whole program, which keeps it exactly right. Diagnostics are published for every open file the check reaches, not just the edited one, and cleared for files that no longer have any.
2. **Check only what changed**, if step 1 leaves the check over 50 ms on the largest program here: keep each function's check results, keyed by its own text and the signatures it uses, and recheck only functions whose key changed. This needs the checker's global tables split per function, so it is a larger change; the plan measures before committing to it.

Both steps change only the OCaml language server (the self-hosted compiler has none). Measured on `selfhost/limen.lmn` and the largest example before and after.

## Not here

- The outside security review (0.9).
- x86-64 Linux on real hardware: there is none to run on; emulation stays the check.
- `exec-missing` under emulation: an emulator limitation, not a bug.
- The `volatile` cast in `cgen.ml`: documented as safe in practice, and the alternative changes every function's C.

## Done when

CI is green on all three runners, the full local pass (suite, `check.sh`, bootstrap fixed point, book, Linux arm64 and amd64) is green apart from what emulation cannot run, SPEC.md and ROADMAP.md say what was done, and the design doc is updated.
